## Executive assessment

The default experiment is careful and honest. The pinned upstream pickle is digest-verified, statically audited
against allow-lists (audit digest pinned), unpickled once into a code-free config + safetensors pair and rebuilt
strictly from `mace-torch`; the model is then checked for rotation, translation and permutation invariance,
gradient-consistent forces and extensivity before any accuracy number is read; the frozen model is scored beside a
composition baseline and a zero-force baseline on the same held-out split; and the EMT-versus-PBE framing makes the
adaptation story meaningful while saying plainly that nothing here speaks to DFT accuracy. A direct CPU execution in
this review reproduced the recorded Kaggle numbers exactly.

Four problems stop it being ready. **Run all does not complete in one pass**: the only hosted record of this exact
blob shows the install cell raising its restart guard, and the run passed only after the executor restarted the
kernel, yet README, STATUS and the tutorials index call it Release-grade. **The documented optional experiments and
the BYOD re-run both continue from the already-adapted model**: `pipe.adapt` never returns to the base weights, so the
`TRAINABLE_BLOCKS = 0` experiment labels an adapted model "frozen model after E0 calibration", and its exported
adapter, overlaid on a fresh base, disagrees with memory by 5.36 eV — the cell's parity assertion fails after the good
adapter has already been deleted (direct CPU execution, P2). The BYOD re-run prints an adapted model's 0.0047 eV/atom
as the "frozen foundation model" error, against the true 3.98 (P3). **The BYOD split contradicts the notebook's own
advice**: it shuffles frames within each composition, so frames of one trajectory land in train and test, and a
dataset with one structure per composition is refused outright (P5). Seven Minor findings cover the BYOD size
contract, a Colab-only upload branch, a missing UNC6 statement, evidence and spec-version gaps, a thin guided layer,
a template-text defect, and an undocumented process-wide `torch.load` default flip.

No finding here says the recorded default-path numbers are wrong.

## 2. Separate judgments

**Technical correctness.** Strong on the default path: identity carried twice and asserted, digest checks before any
deserialisation, a static audit of every global and generated source the pickle would execute, a single audited
unpickle, strict loads, transactional `adapt`, digest-checked adapter, physics assertions. Defects: the in-kernel
install cannot complete Run all in one pass on the recorded hosted image (MMC-M1); Section 7 is not re-entrant, so
re-running it continues from adapted weights and can export an adapter that does not reproduce the model (MMC-M2,
MMC-M3); the BYOD split and size contract fail for common data shapes (MMC-M4, MMC-m1).

**Promise fulfilment.** The default promises are delivered and evidenced by the exact-blob Kaggle run, apart from "The
default path needs no … configuration edit" / one-pass Run all (MMC-M1). The optional-experiment promise ("watch the
forces stay put") cannot be observed as stated because the experiment starts from an adapted model (MMC-M2). The BYOD
promise ("the same validation, composition-stratified split, baselines, calibration, adaptation, held-out evaluation …
as the generated sample") is not delivered: the baselines and adaptation are contaminated by the sample run (MMC-M3),
and the split is not held-out for trajectory data (MMC-M4).

**Learner experience.** The prose is accurate and unusually well-motivated: it explains why the frozen energies are
eV/atom off, what each baseline can and cannot see, why the physics checks come first, and what the result does not
establish. But a 60 KB carried module cell has no Infrastructure label, and there is no how-to-use, roadmap, glossary,
prediction, checkpoint, troubleshooting or conclusion scaffold (MMC-m5).

**Spec conformance.** Unresolved applicable `MUST`s: RUN1, RUN10, ENV6, REL2/REL11 (MMC-M1); SRC2, VER4/VER5, OUT8,
ART8 on the documented experiment path (MMC-M2); DAT13, DAT14 (MMC-M3); SPL3, SPL5 (MMC-M4); DAT12, DAT19, REL12
(MMC-m1); UNC6 (MMC-m3); SRC3 (MMC-m6). Several `SHOULD`s in the GDL and EXE families (MMC-m2, MMC-m5).

## 5. Findings

### Major

#### MMC-M1 — Run all stops at the install cell's restart guard on the only hosted run of this blob

- **Cell/section:** Section 1, cell 3 (generator `tools/build_notebook.py:57–69`).
- **Observed issue:** the cell `pip install`s `torch==2.14.0`, `numpy==2.5.3` and the other pins into the running
  kernel, then raises `RuntimeError … Restart the runtime, then rerun from the top.` when a loaded distribution
  changed. On the Kaggle T4 run of blob `1044b4aa` it fired (cuda-bindings 12.9.4 → 13.4.2, numpy 2.0.2 → 2.5.3); the
  run passed only on an executor-driven second pass. `docs/release-verification.md` step 4 even says "an interpreter
  restart after the install is expected", while the opening cell promises no intervention. README, STATUS and
  `tutorials/README.md` call the notebook Release-grade on this record.
- **Consequence:** a learner choosing Run all on a fresh hosted runtime hits an error at the first code cell; the
  release status contradicts RUN10.
- **Evidence:** documented execution evidence (`run_summary.json`, pass 1 `ok: false`, pass 2 `ok: true`).
- **Recommended correction:** replace the in-kernel install with the fleet's uv isolated-environment pattern: a
  carrier cell bootstraps uv, creates `uv venv --managed-python --python 3.12.12 <ROOT>/env`, installs a hash-locked
  `requirements.txt` with `uv pip install --require-hashes --only-binary :all:`, and runs the workload in that env, so
  the kernel's preloaded NumPy/torch are never replaced (reference:
  `ast-audio-classification-pipeline/tutorials/DIMER_Sound_Event_Classification_Workshop.ipynb` on `main`). Change it
  in `tools/build_notebook.py` / `tools/notebook_template.py`, regenerate, and remove the "restart … is expected"
  sentence from `docs/release-verification.md`. Return the status token to Candidate until a one-pass run is recorded.
- **Acceptance check:** a fresh Colab (or Kaggle) runtime executes every code cell of the regenerated notebook in one
  pass with no restart and no error output; the record in `docs/release-verification.md` says "1 pass, 0 restarts"
  for that blob.
- **Spec:** RUN1, RUN10, ENV6, REL2, REL11.

#### MMC-M2 — The documented experiments re-run `adapt` on the already-adapted model; the exported adapter then fails reload parity

- **Cell/section:** Section 7 (cell 18 prose, cell 19), Interpretation (cell 24 "Optional experiments"); package
  `pipeline.py` `adapt()` (no reset to base); template `tools/notebook_template.py:285–286, 460`.
- **Observed issue:** `adapt()` starts from `self.model` as it is. After the default run, setting
  `TRAINABLE_BLOCKS = 0` and re-running Sections 7–9 (no rerun instruction is given) trains readouts on top of the
  adapted last block. Epoch 0, labelled "frozen model after E0 calibration", scores 0.00502 eV/atom (true: 0.0985). The
  new adapter holds only the 12 readout/E0/scale tensors, so `from_artifact` (fresh base + adapter) differs from
  memory by 5.36 eV energy and 2.29 eV/Å force; the assertion fires only after `shutil.rmtree` has removed the good
  adapter. The prose claim that the readouts-only arm "barely moves forces" cannot be observed this way.
- **Consequence:** the notebook's only learner-driven experiment produces a mislabelled baseline, a stacked training
  run presented as a single one, and a broken export.
- **Evidence:** direct execution, local CPU (P2).
- **Recommended correction:** make `adapt()` start from the converted base weights every call (restore a stored base
  `state_dict` at entry, or rebuild via `from_pretrained`), record that in the manifest, and add explicit rerun
  instructions ("change the field, then run Section 7 onward"). Alternatively the notebook rebuilds `pipe` at the top
  of Section 7. Add a regression test: two consecutive `adapt` calls with different `trainable_blocks` give the same
  epoch-0 metrics and reload parity.
- **Acceptance check:** after a default run, `TRAINABLE_BLOCKS = 0` + re-run of Sections 7–9 shows epoch-0 validation
  equal to the default run's epoch 0 (0.0985 eV/atom on the sample, within 1e-9) and reload parity below 1e-9.
- **Spec:** GDL10, UX7, SRC2, VER4, VER5, OUT8, ART8.

#### MMC-M3 — BYOD "re-run from that cell" reports the sample-adapted model as the frozen foundation model

- **Cell/section:** opening cell (BYOD paragraph), Section 4 (cell 13), Section 6 (cell 17); template
  `tools/notebook_template.py:68`.
- **Observed issue:** the instructions say to set `USE_BYOD = True` after the tutorial completes and re-run from
  Section 4. `pipe` still carries the sample adaptation, so Section 6 prints it as `frozen_foundation_model`, and the
  BYOD adaptation, comparison table, report and adapter all start from sample-adapted weights.
- **Consequence:** the learner's central BYOD comparison (frozen vs adapted on their data) is wrong — on the probe
  input the "frozen" energy error was 0.0047 eV/atom instead of 3.98 — and the adapter manifest does not record the
  prior training.
- **Evidence:** direct execution, local CPU, upload shimmed (P3).
- **Recommended correction:** the same base reset as MMC-M2, plus re-creating `pipe` (or asserting
  `pipe.adapter is None`) at the top of Section 6 with a message naming the cell to re-run.
- **Acceptance check:** after a default run, a BYOD re-run with the sample XYZ prints the same Section 6
  `frozen_foundation_model` numbers as the default run (3.98 / 0.208 on the sample split).
- **Spec:** DAT13, DAT14, EVAL10, OUT8, ART8.

#### MMC-M4 — The BYOD split shuffles frames within each composition, against the notebook's own advice

- **Cell/section:** Section 4 (cell 12 prose, cell 13); package `samples.py` `split_dataset`; Interpretation cell 24
  ("split by trajectory or by composition, never at random over frames").
- **Observed issue:** `split_dataset` groups by composition and shuffles inside each group, so frames of one
  trajectory or relaxation (one composition) are spread over train, validation and test. There is no group field. A
  dataset with one structure per composition is refused (`split leaves no training structures`), since every
  composition must contribute at least one test structure.
- **Consequence:** for the user data the notebook itself calls typical, the "independent test split" is leaky and the
  held-out numbers are inflated; for multi-stoichiometry data BYOD cannot run.
- **Evidence:** direct execution of the carried `split_dataset` (P5: 12 frames of one trajectory → 7/2/3; 8
  single-composition records → refused).
- **Recommended correction:** accept an optional group key (per-frame `info['group']` or `info['trajectory']` in the
  extended XYZ, exposed as a form field), split by group when present, fall back to the composition-stratified split
  only when absent, and state the independence assumption in Section 4. Say what to do with one structure per
  composition (group split by composition, or random split with the assumption stated).
- **Acceptance check:** a BYOD XYZ whose frames carry `trajectory=A..D` yields splits in which no trajectory appears in
  two splits; an 8-record one-per-composition file either completes or is refused with a message naming the group
  rule and the fix.
- **Spec:** SPL3, SPL5, DAT12, DAT13.
